# zDashboard 顶层设计

## 项目定位

个人数据中心。在信息过载的时代，将信息摄取、知识内化、数据整理三条链路收回自己手中。

不做 SaaS，不做多用户，不做通用平台。一切设计为自己服务。

---

## 核心模块

### 1. 信息整合（Information Hub）

**动机**：互联网信息密度持续下降，推荐算法稀释内容质量。不再依赖平台推送，转为主动管控信息源。

**定位**：与 Vocab 平级的一等模块。核心问题是「什么东西值得我花时间看」，而非「怎么收藏更多东西」。

**方向**（待细化）：
- 信息源管理：定义、筛选、评级你的信息来源
- 内容聚合：将分散的信源统一到单一收件箱
- 质量过滤：低信息密度的内容不应进入视野

### 2. 英语学习（Vocab）

**当前状态**：已可用。文章提交 → 分词 → 逐词标状态。

**演进方向**：
- 词汇量度量：建立足够大的系统词库，已掌握词数即词汇量估值，无需独立测试模块
- 文章搜寻/生成：为词汇量度量提供持续语料输入
- 数据结构升级：从简单三态升级为多维度词状态跟踪

### 3. 媒体播放

**状态**：已于 v0.2.0 删除。路由、WebSocket、前端播放条、`ws` 依赖全部移除，后续重做。

## 同步架构

**现状**：主力部署在本地服务器，公网 VPS 性能不足以承载完整服务。移动端或外网场景下无法直接访问。

**原则**：
- 不废弃现有前后端 Web 架构。浏览器直连服务器仍是主路径。
- Git 同步作为扩展通道：解决「不在本地网络时如何交换数据」的问题。
- 数据中转为 GitHub/Gitee 仓库。本地 push，远端 pull，反之亦然。

**形态**（待细化）：
- 哪些数据走 Git 同步（全文？摘要？操作日志？）
- 冲突如何处理（谁先写谁赢？最后写赢？合并策略？）
- 前端如何感知当前数据来源（直连 vs Git 同步）

---

## 不做的

- 多用户、权限、登录系统
- 构建步骤、前端框架、TypeScript 迁移
- Diary、Finance、Reminders 等占位模块 —— 保持硬编码占位，不纳入当前开发计划

---

## 技术约束（不变）

- 后端：Node.js + Express + SQLite（better-sqlite3）
- 前端：单文件 SPA，无构建步骤
- 部署：本地服务器为主，.run 便携包为辅
- 数据库：SQLite WAL 模式，写事务后调用 `checkpoint()`（本机 throttle / 容器 always）
